# tomaTime 生成 AI 開発環境の改善報告

報告日　2026年11月25日  
対象　tomaTime の要求定義、要件定義、設計、実装・テストを支援する Claude Code 環境

## 1. 要旨

tomaTime は、生成 AI が現在時刻を参照できるよう、OS の時計から取得した時刻を HTTP で返すサーバーです。この案件を使い、AI への作業指示、成果物の書式、人による判断、機械検査を見直しました。改善前の要求書と実行ログを調べ、重要な確認が遅れること、判断の出典が混在すること、文書と実行時の指示が食い違うことを優先して対応しました。

要求定義を11プロセスにそろえ、成果物の置き場所を明確にしました。重要事項は発見時点で人に確認し、要求書と要件定義書はそれぞれ AI 一次レビュー1回と人の承認を経て次に進みます。フェーズ移行の検査は人が読める JSON にまとめ、成功時の時刻本文は作業ファイル上の正本を各担当が参照する構成にしました。[プロジェクトの運用ルール](../CLAUDE.md)

## 3. スキルとエージェントの構成

メインのセッションは、現在のフェーズを確認して、対象文書のパス、依頼・回答の原文、担当範囲を渡します。重要事項の質問と人への承認依頼もメインが担当し、AI レビューの指摘は作成担当が反映します。[エージェントの共通ルール](../.claude/rules/agents.md)

| スキル | 担当エージェント | 成果物・次工程への引き継ぎ |
|---|---|---|
| [`request-intake`](../.claude/skills/request-intake/SKILL.md) | `request-analyst` が調査と要求書を担当。`request-reviewer` が依頼原文との対応、要求漏れ、推測、確認事項を点検 | 要求書、確認事項、一次レビューの指摘と対応。人が要求書を承認 |
| [`requirements-definition`](../.claude/skills/requirements-definition/SKILL.md) | `requirements-engineer` が要件を定義。`requirements-reviewer` が要求との対応、インターフェース、検証可能性を点検 | 機能・非機能要件、インターフェース仕様、受け入れ条件。人が要件定義書を承認 |
| [`implement-test`](../.claude/skills/implement-test/SKILL.md) | `software-designer` が設計、`ts-developer` が本番実装、`test-engineer` がテスト、`code-reviewer` がコードレビューを担当 | 設計書、本番コード、受け入れテスト、レビュー結果。検査通過後に完了 |

要求定義は、戦略と目的 → スコープ → 対象ユーザー → 現状調査 → 経営・業務・情報ニーズ → 成功要因と管理指標 → 用語と指標の定義 → データの粒度 → 非機能要求 → アプリケーションの種類とツール要件 → 文書化の順に進めます。各プロセスの結果を次の判断に使い、調査方法と資料の量は案件に合わせます。[要求定義の11プロセス](../.claude/skills/request-intake/002_workflow/008_要求定義の11プロセス.md)

要求・要件定義のレビュアーは読み取り専用です。コードレビュアーは型検査とテストのコマンドを実行し、編集は担当に戻します。文書テンプレートは章単位で、要求 ID から機能要件、設計、受け入れ条件への対応を記録します。[文書の構成](../docs/README.md)、[コードレビュアーの定義](../.claude/agents/code-reviewer.md)

## 4. ハーネスの検査範囲

`pipeline.mjs advance` はフェーズごとの定義を上から実行し、最初の不合格で理由を返してそのフェーズに留まります。人の「承認」をフックが記録し、移行時に現在の文書のハッシュと照合します。[パイプライン CLI](../.claude/harness/pipeline.mjs)、[承認フック](../.claude/harness/user-prompt.mjs)

| フェーズ | 自動検査の内容 |
|---|---|
| 要求 | 要求書のフォルダ・章構成、要求一覧と確認事項の見出し、`REQ-n` の存在 |
| 要求レビュー・要件レビュー | 対象文書への承認の有無、承認時の SHA-256 ハッシュとの一致 |
| 要件定義 | 要件定義書の章構成、各 `FR-n` に対応する `FR-n-AC-m` の存在、要求書の `REQ-n` が要件定義書に現れること |
| 実装テスト | npm スクリプトの定義、受け入れ条件 ID がテストファイルに現れること、設計書・レビュー結果の章構成、型検査・テストの終了コード |

ID 検査は本文のパターン一致までを扱います。要求とテストの対応の意味、必須章の内容、AI 一次レビューの実施回数は、手順とレビューで確認します。書き込みガードには担当別の制限があり、フェーズ別の書き込み制限は現行コードで無効です。要件検査には `NFR-n` の一部を `FR-n` として拾う可能性も残っています。[検査定義と補足](../.claude/harness/pipeline-checks.json)、[書き込みガード](../.claude/harness/guard-write.mjs)
