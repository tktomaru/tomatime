# docs

パイプライン（要求 → 要件定義 → 設計 → レビュー）の文書を置く。番号は作業の順で、若い工程ほど小さい。

成功時の時刻の返却形式は [正本](../.claude/specs/time-response-format.md) を参照する。承認済みの要求書・要件定義書にある書式や参照先は承認時点の記録として扱う。新しい文書で形式を示す場合は正本を参照し、受け入れ条件には検証する本文の具体値を書く。

| 番号の範囲 | 用途 |
|---|---|
| `001`〜 | 工程の成果物（作業の順） |
| `900`〜 | 資材（テンプレートなど、工程ではなく参照するもの） |

## 構成

| フォルダ | 内容 | 作成者 | フォーマット例 |
|---|---|---|---|
| `001_requests/` | 要求書 | request-analyst | `900_templates/001_request/` |
| `002_requirements/` | 要件定義書 | requirements-engineer | `900_templates/002_requirements/` |
| `003_designs/` | 設計書 | software-designer | `900_templates/003_design/` |
| `004_reviews/` | レビュー結果 | メインのセッション（code-reviewer の返却を保存） | `900_templates/004_review/` |
| `900_templates/` | フォーマット例（資材） | - | - |
| `910_knowledge/` | ノウハウ（資材。判断の参考にする） | - | - |

```
docs/001_requests/001_time-server/
  README.md                 表題と章の目次
  001_背景・目的.md         1 章 1 ファイル（「## 背景・目的」の見出しから始める）
  002_利用者と利用場面.md
  ...
```

## 名前の決まり

ハーネス（`.claude/harness/guard-write.mjs`、`pipeline.mjs`）が検査する。

| 対象 | 形式 | 例 |
|---|---|---|
| フォルダ | 3 桁の連番 + `_` + 英小文字・数字・ハイフン（機能名はパイプラインと共有するため英語） | `001_requests`、`001_time-server` |
| 章ファイル | 3 桁の連番 + `_` + 章の見出し（`## ` の後ろと同じ文字列）+ `.md`。001 から欠番なし。空白と `\ / : * ? " < > \|` は使わない | `001_背景・目的.md` |
| 上記以外のファイル | `README.md`（目次）、`.gitkeep` のみ | - |

- 1 つの文書は `<種類のフォルダ>/<NNN>_<機能名>/` に置く。`<NNN>` は要求書のフォルダで決めた番号で、要件定義書・設計書・レビュー結果も同じ番号を使う
- 現在の機能の文書のパスは `node .claude/harness/pipeline.mjs status` が表示する
- 文書の本文は、章ファイルを番号順に連結したものとして扱う。章の順番と見出しはフォーマット例に合わせる
- 承認は文書のフォルダ単位で記録される。承認後にフォルダ内のファイルを変更・追加・削除すると、承認を取り直す必要がある
