## 実務で守る最終ルール

本プレイブックを日々の開発へ圧縮すると、守るべき原則は次に集約できる。アーキテクチャの中心価値は、ソフトウェアの「柔らかさ」、すなわち変更可能性を守ることである。Web、DB、フレームワーク、サービス形態は重要ではあるが、ビジネス方針を支配する中心概念ではなく詳細である。重要なのは、どこに境界を置き、どちら向きに依存させ、何を変更から保護するかである。

設計時には、次の順で考える。

1. **目的から始める。** 技術選定から始めない。
2. **ユースケースを明示する。** システムが何をするかを構造に表す。
3. **将来の変更を想定する。** 頻繁で重要な変更から守る。
4. **変更理由が異なるものを分ける。** SRP/CCPを使う。
5. **重要な方針を中心へ置く。**
6. **依存方向を方針側へ向ける。**
7. **DB、Web、UI、フレームワーク、外部APIを詳細として扱う。**
8. **交換可能性を保つ。** 実装固有の条件分岐を中心へ入れない。
9. **境界を作りすぎない。** 将来の仮説だけで抽象化しない。
10. **品質特性を数値にする。** 「高速」「高可用」で終わらせない。
11. **トレードオフを記録する。** メリットだけで決定しない。
12. **テストできない構造を疑う。**
13. **観測できない構造を疑う。**
14. **セキュリティを後付けにしない。**
15. **ADRで前提を残す。**
16. **図は相手の関心事ごとに描き分ける。**
17. **物理分割を論理分割より先にしない。**
18. **全面リライトより境界を一つずつ改善する。**
19. **アーキテクチャを仮説として計測する。**
20. **変更コストが実際に下がったかで成功を判定する。**

この最後の二点が特に重要である。**「Clean Architectureを採用した」「DDDを採用した」「マイクロサービス化した」は成果ではない。** 典型的な変更が局所化され、リードタイムが短縮し、障害波及が減り、テストが容易になり、開発者がシステムを理解しやすくなったとき、初めてアーキテクチャ改善が成功したと言える。この考え方とSEIの継続的アーキテクチャ評価を合わせると、アーキテクチャとは固定された完成図ではなく、**変更・検証・学習を繰り返しながら、システムの重要な方針と将来の選択肢を守り続ける仕組み**と捉えるのが最も実践的である。
