## 品質特性・トレードオフ・設計判断

### 非機能要件を「形容詞」で終わらせない

「高可用」「高速」「拡張可能」「セキュア」は設計要件として不十分である。SEIは品質特性をシナリオベースで分析する手法を長年研究しており、ATAMでは性能、可用性、セキュリティ、変更容易性などに影響するアーキテクチャ判断のリスクとトレードオフを体系的に評価する。

品質要件は、最低でも次の形で書く。

```text
刺激源:
刺激:
環境:
対象:
応答:
応答尺度:
```

例：

```text
刺激源: 一般ユーザー
刺激: 商品検索APIを呼ぶ
環境: ピーク時 2,000 req/s
対象: Search API
応答: 正常結果または明示的な縮退結果を返す
応答尺度:
  p95 < 300ms
  p99 < 800ms
  error rate < 0.1%
```

AWS Well-Architected Frameworkも、運用性、セキュリティ、信頼性、性能効率、コスト最適化、持続可能性の六つの柱を用い、ビジネス要件に応じたトレードオフを明示する考え方を採っている。これはAWSを使用していなくても、品質特性の漏れ確認リストとして参考になる。

### 品質特性には必ずトレードオフがある

| 選択 | 主なメリット | 主なデメリット |
|---|---|---|
| キャッシュ | レイテンシ低下、DB負荷低減 | 不整合、無効化複雑化 |
| 非同期化 | ピーク吸収、可用性向上 | 一貫性・追跡・再処理が複雑 |
| マイクロサービス | 独立デプロイ・スケール | ネットワーク障害、観測、運用負荷 |
| DB分割 | データ所有権明確化 | JOIN・トランザクション困難 |
| 強整合性 | 推論しやすい | レイテンシ・可用性との競合 |
| 多重化 | 可用性向上 | コスト・運用複雑性増 |
| 抽象化 | 変更隔離 | 認知負荷・実装量増 |
| イベント駆動 | 疎結合 | デバッグ・順序・重複処理が難化 |

**判断ルール。** 「何を得るか」だけでADRを承認しない。「何を悪化させるか」を必須項目にする。

### サービス分割はアーキテクチャ境界と同義ではない

非常に重要な点として、**サービスであること自体はアーキテクチャ境界を意味しない**。サービスはスケーラビリティや開発上便利でも、アーキテクチャを定義するのは境界とその境界を横切る依存関係であり、通信方式ではない。

したがって、

```text
1 process = monolith = bad
10 services = microservices = good
```

という判断は成立しない。

モノリス内部でも依存方向が整理されていれば優れた境界を持てる一方、マイクロサービスでも全サービスが同じDBを共有し、同期呼出しで鎖状につながり、同時デプロイ必須なら「分散モノリス」である。

**マイクロサービス化の判断条件。**

- 独立デプロイが実際に必要か。
- 独立スケールが必要か。
- チーム所有権が明確になるか。
- データ所有権を分割できるか。
- ネットワーク障害を前提にできるか。
- 分散トレーシング、再試行、冪等性、タイムアウトを運用できるか。
- 分割による運用コストを支払う価値があるか。

一つでも不明なら、まずモジュラーモノリスで境界を検証する方が安全である。これは「境界を物理デプロイ方式と混同しない」という原則から導く実務的推論である。

### データベースは中心ではない

DBは「詳細」と位置付ける。これはDBが重要ではないという意味ではない。**DB製品・ストレージ方式がビジネス方針を支配してはいけない**という意味である。

悪い設計はテーブル構造からアプリケーションを設計する。

```text
TABLE order
   ↓
OrderEntity
   ↓
OrderRepository
   ↓
OrderService
   ↓
OrderController
```

良い設計では、まずユースケースの必要性からデータアクセス契約を決める。

```text
ConfirmOrder
   ↓
OrderRepository.getForConfirmation()
   ↑
SqlOrderRepository
```

Humble Objectの考え方でも、DB Gatewayをアプリケーション側のポリモーフィックなインターフェイスとして置き、ORMをDB側の詳細へ配置する。

### Web・UI・フレームワークも詳細として扱う

Webは一種のI/Oデバイスであり、Webで提供するという決定がユースケースやビジネスルールを支配すべきではない。またフレームワークは「ツール」であってシステムの生き方そのものではない。

典型的な危険信号は以下である。

```java
@Entity
@RestController
public class Order {
    ...
}
```

同一クラスにORM、HTTP、ドメイン意味論が混在しているなら、フレームワーク変更だけで中心モデルが変わる。

一方、全てのプロジェクトで「純粋ドメインモデル」とORMモデルを二重管理する必要があるわけではない。CRUD中心の単純な管理画面なら、分離コストが便益を上回る可能性がある。境界は「変更可能性」と「重要性」に比例させるべきである。

### テスト可能性をアーキテクチャ特性として扱う

テストはシステムの外付け物ではなく、最も独立したシステムコンポーネントとして扱う。テストを設計に統合しない場合、システムは硬直化する。またテストは依存性のルールに従い、プロダクションコードがテストコードへ依存してはならない。

設計レビューでは次を実際に試す。

```text
DB停止
Web停止
Kafka停止
外部APIモック
```

この状態で重要ユースケースのテストが動けば、境界が機能している可能性が高い。

テスト分類の目安は次のようにする。

| 対象 | 主目的 | 速度 | 本数 |
|---|---|---:|---:|
| Domain | ビジネスルール | 最速 | 多 |
| Use Case | アプリケーション方針 | 高速 | 多 |
| Adapter Contract | 境界契約 | 中 | 中 |
| Integration | DB/外部連携 | 中〜低 | 中 |
| E2E | 全体成立 | 低速 | 少 |

### 運用可能性も設計時に組み込む

Google SREはユーザー向けサービスの基本的な監視信号として latency、traffic、errors、saturation の四つを挙げている。運用性は完成後に監視ツールを追加して得るものではなく、アーキテクチャ段階で「何を観測すれば仮説が検証できるか」を決める必要がある。

最低限、各重要ユースケースに対して次を決める。

```text
SLI:
  成功率
  レイテンシ
  スループット
  キュー滞留時間
  リトライ回数

ログ:
  correlation_id
  actor
  use_case
  result
  elapsed_ms

トレース:
  外部API
  DB
  Message Broker
```

アーキテクチャ判断が正しかったかどうかは、本番計測がなければ判断できない。

### セキュリティを境界設計に統合する

NISTのZero Trust Architectureは、ネットワーク位置や所有主体だけを理由に暗黙の信頼を置かず、アクセス対象となるリソース、ユーザー、デバイスを中心に認証・認可を行う考え方を採っている。

OWASPもASVSでArchitecture, Design and Threat Modelingを独立した検証領域として扱い、Threat Modelingでは「何を作っているか」「何が問題になり得るか」「どう対処するか」「十分対応できたか」という反復的な問いを使うことを推奨している。

実務では、新しい境界を作るたびに以下を問う。

```text
Trust Boundaryはどこか
誰が呼べるか
何を認証するか
何を認可するか
入力はどこで検証するか
秘密情報はどこに置くか
監査ログは必要か
Replayは問題になるか
DoS時にどこが枯渇するか
```
