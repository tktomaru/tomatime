## 処理の流れ

### 要求 1 件の処理（M-4）

判定の順は要件定義書の FR-5 の補足（FR-6 → FR-5 → FR-4・FR-10 → FR-1・FR-10）に従う。手順 2〜6 は 1 つの `try` の中で行い、手順 7 はその `catch` から入る。

| 順 | 処理 | 担当モジュール | 失敗したとき |
|---|---|---|---|
| 1 | Node.js の `http` が要求を解析し、受け付けた要求だけ M-4 の処理を呼ぶ | M-5（Node.js の既定） | Node.js の既定のエラー応答（400、408、417、431）。M-4 は呼ばれず、取得元も呼ばれない（FR-6） |
| 2 | `req.method` を読み、`GET` と `HEAD` 以外なら 405 の応答の内容を組み立てて手順 6 へ進む。取得元を呼ばない | M-4 | 手順 7（`internal`） |
| 3 | 取得: `deps.clock()` を 1 回だけ呼ぶ。呼び出しを専用の `try` で囲む | M-4 → M-1 | 取得元の例外は `source-threw` として手順 8 へ（手順 7 を通らない） |
| 4 | 整形: `formatJst(raw)` を呼ぶ（M-2 の手順は下の「整形（M-2）」） | M-2 | `ok: false` なら理由（`non-finite` / `out-of-range`）で手順 8 へ。例外は手順 7（`internal`） |
| 5 | 200 の応答の内容（ステータス、ヘッダー、本文、`Date` の有無）を組み立てる | M-4 | 手順 7（`internal`） |
| 6 | 送信: `res.sendDate` を設定し、`res.writeHead(status, headers)` の後、`GET` なら `res.end(body)`、`HEAD` なら `res.end()` | M-4 | 手順 7（`internal`） |
| 7 | 例外の受け止め（`catch`）: 受け止めた値を `{ kind: 'internal', thrown }` にして手順 8 へ | M-4 | - |
| 8 | 1 行の書き込み: `failureLine(failure)` で 1 行を作り、`deps.writeErrorLine(line)` を 1 回呼ぶ。組み立てと書き込みを専用の `try` で囲む | M-3, M-4 | 例外は捨てる。1 行は出ず、手順 9 へ進む（FR-4 の補足） |
| 9 | 500 の送信: `res.headersSent` が false なら `res.sendDate = false` にして 500 の応答を送る（`HEAD` は本文なし）。true なら `res.destroy()` で接続を切る。全体を専用の `try` で囲む | M-4 | 例外なら `res.destroy()` を呼ぶ（その例外も捨てる）。時刻の形式の値は送らない |

- 手順 3〜6 で使う時刻と本文は、その要求の処理の中のローカル変数だけに置き、処理が終われば参照を捨てる（NFR-1）
- 応答の内容（手順 2 と 5）を組み立て終えてから送信（手順 6）するので、送信の前に起きた例外では何も送られていない。手順 9 はその場合に 500 を送る
- 手順 6 の `writeHead` の後で例外が起きた場合（`headersSent` が true）は、ステータスを変えられないため接続を切る。`res.end(body)` は本文を 1 回で渡すので、本文の一部だけが送られる経路はない
- 手順 8 を手順 9 より前に行うのは、テストが応答を受け取った時点で 1 行が書き込み先に渡り終えているようにするため（受け入れ条件の「その要求の処理の間に渡された文字列」）
- M-4 の処理は例外を Node.js へ投げ返さない（`createRequestHandler` が返す関数は必ず正常に戻る）

処理の骨格（ts-developer への指示。名前は実装で変えてよいが構造は変えない）。

```ts
export function createRequestHandler(deps: HandlerDeps) {
  return (req: IncomingMessage, res: ServerResponse): void => {
    const isHead = req.method === 'HEAD';
    try {
      if (req.method !== 'GET' && !isHead) {
        send(res, isHead, plan405());            // 取得元を呼ばない
        return;
      }
      const result = readAndFormat(deps.clock);   // 取得（専用の try）と整形
      if (!result.ok) {
        fail(res, isHead, result.failure, deps.writeErrorLine);
        return;
      }
      send(res, isHead, plan200(result.text));
    } catch (thrown) {
      fail(res, isHead, { kind: 'internal', thrown }, deps.writeErrorLine);
    }
  };
}

function readAndFormat(clock: Clock):
  | { ok: true; text: string }
  | { ok: false; failure: TimeFailure } {
  let raw: unknown;
  try {
    raw = clock();
  } catch (thrown) {
    return { ok: false, failure: { kind: 'source-threw', thrown } };
  }
  const formatted = formatJst(raw);              // ここでの例外は呼び出し元の catch で internal になる
  return formatted.ok
    ? { ok: true, text: formatted.text }
    : { ok: false, failure: { kind: formatted.reason } };
}

function fail(res: ServerResponse, isHead: boolean, failure: TimeFailure, write: ErrorLineWriter): void {
  try { write(failureLine(failure)); } catch { /* 書き込みの失敗は応答に影響させない */ }
  try {
    if (res.headersSent) { res.destroy(); return; }
    send(res, isHead, plan500());                // sendDate = false、本文 time unavailable
  } catch {
    try { res.destroy(); } catch { /* 何もしない */ }
  }
}
```

### 整形（M-2 `formatJst`）

| 順 | 処理 | 担当モジュール | 失敗したとき |
|---|---|---|---|
| 1 | `typeof epochMs === 'number' && Number.isFinite(epochMs)` を確かめる | M-2 | `{ ok: false, reason: 'non-finite' }` を返す（`NaN`、`Infinity`、`-Infinity`、数でない値） |
| 2 | 日本時間のミリ秒 `jst = epochMs + 32_400_000`（9 時間）を求め、秒未満を切り捨てる: `sec = Math.floor(jst / 1000) * 1000` | M-2 | - |
| 3 | `sec` が `MIN_JST_MS = -62_135_596_800_000`（`0001-01-01 00:00:00`）以上、`MAX_JST_MS = 253_402_300_799_000`（`9999-12-31 23:59:59`）以下かを確かめる。`Date` を作る前に行う | M-2 | `{ ok: false, reason: 'out-of-range' }` を返す |
| 4 | `const d = new Date(sec)` から `getUTCFullYear`、`getUTCMonth() + 1`、`getUTCDate`、`getUTCHours`、`getUTCMinutes`、`getUTCSeconds` を読み、年は 4 桁、ほかは 2 桁に `padStart(n, '0')` でゼロ埋めし、`-`、半角空白、`:` でつなぐ | M-2 | 例外は投げたままにする（M-4 で `internal`） |
| 5 | できた文字列が `/^[0-9]{4}-[0-9]{2}-[0-9]{2} [0-9]{2}:[0-9]{2}:[0-9]{2}$/` に一致することを確かめ、`{ ok: true, text }` を返す | M-2 | 一致しなければ `Error` を投げる（M-4 で `internal`。500 になる） |

- 有効範囲の境界は、要件定義書の FR-4-AC-3〜FR-4-AC-6 の値で次のようになる: UTC `9999-12-31T14:59:59.999Z` → `sec` = `MAX_JST_MS`（200）、UTC `9999-12-31T15:00:00.000Z` → `MAX_JST_MS + 1000`（500）、UTC `0000-12-31T15:00:00.000Z` → `sec` = `MIN_JST_MS`（200）、UTC `0000-12-31T14:59:59.999Z` → `MIN_JST_MS - 1000`（500）
- 境界の数値は定数として書き、`Date.UTC(1, 0, 1)` で作らない（`Date.UTC` は年 0〜99 を 1900 年代として扱うため）
- `Math.floor` による切り捨ては、`Date.now()` が返す整数のミリ秒では誤差なく前の秒に丸める（有効範囲の秒数の絶対値は 2.6 × 10^11 未満で、2^53 / 1000（約 9.0 × 10^12）より小さいため、商の丸めで整数をまたがない）
- 手順 5 は防御のための検査で、通常は必ず一致する。一致しない文字列を本文にしない（TS-5）

### 起動（M-7 `npm start`）

| 順 | 処理 | 担当モジュール | 失敗したとき |
|---|---|---|---|
| 1 | `process.stderr.on('error', () => {})` を登録する（標準エラー出力の非同期の書き込み失敗でプロセスが落ちないようにする） | M-7 | - |
| 2 | `parseConfig(process.env)` を呼ぶ。検査の順は `TOMATIME_HOST`、`TOMATIME_PORT` | M-7 → M-6 | `ok: false` なら `startup failed: invalid <名前>` と LF を標準エラー出力に書き、`process.exitCode = 1` にして待ち受けずに戻る（プロセスは自然に終了する） |
| 3 | `createTimeServer({ clock: systemClock, writeErrorLine: (line) => { process.stderr.write(line); } })` を呼ぶ | M-7 → M-5 | - |
| 4 | `process.once('SIGINT', stop)` と `process.once('SIGTERM', stop)` を登録する。`stop` は `process.exit(0)` を呼ぶだけ | M-7 | - |
| 5 | `server.once('error', onStartupError)` を登録し、`server.listen(port, host)` を呼ぶ | M-7 | `onStartupError` は `startup failed: <code> host=<host> port=<port>` と LF を標準エラー出力に書き、`process.exitCode = 1` にする。`code` は `err.code` が文字列ならその値、そうでなければ `UNKNOWN`。シグナルの登録は unref のためプロセスは自然に終了する |
| 6 | `listening` イベントで `server.off('error', onStartupError)` を呼び、`listening: host=<host> port=<port>` と LF を標準出力に書く | M-7 | - |

- `<host>` と `<port>` は M-6 が返した値（環境変数の値そのまま、未設定なら `127.0.0.1` と `3000`）。`port` は `1`〜`65535` の先頭が `0` でない 10 進数なので、数を文字列に戻すと環境変数の文字列と一致する
- 起動の失敗で `process.exit(1)` を呼ばないのは、パイプへ書いた標準エラー出力が終了で切れないようにするため（10 章）
- 起動時の出力に時刻を含めない（要件定義書の「ログ・標準出力・標準エラー出力」）

### 環境変数の検査（M-6 `parseConfig`）

| 順 | 処理 | 担当モジュール | 失敗したとき |
|---|---|---|---|
| 1 | `env.TOMATIME_HOST` が `undefined` なら `127.0.0.1`。そうでなければ値を変換せずに `net.isIP(value)` を呼び、`4` か `6` なら採る | M-6 | `0` なら `{ ok: false, invalid: 'TOMATIME_HOST' }` を返す（空文字列を含む） |
| 2 | `env.TOMATIME_PORT` が `undefined` なら `3000`。そうでなければ `/^[1-9][0-9]{0,4}$/` に一致し、`Number(value) <= 65535` なら採る | M-6 | それ以外は `{ ok: false, invalid: 'TOMATIME_PORT' }` を返す（空文字列、`0`、`080`、`65536`、符号・空白・小数点を含むもの） |
| 3 | `{ ok: true, config: { host, port } }` を返す | M-6 | - |

### 停止（M-7）

| 順 | 処理 | 担当モジュール | 失敗したとき |
|---|---|---|---|
| 1 | SIGINT（Ctrl+C）または SIGTERM（`docker stop`）を受け取る。コンテナでは exec 形式の `CMD` により Node.js が PID 1 として直接受け取る | M-7 | - |
| 2 | `process.exit(0)` を呼ぶ。`server.close()` を待たず、処理中の要求の完了を待たない。終了時に応答を作らない | M-7 | - |

- Windows では外部からの SIGTERM は届かない。開発機の停止は Ctrl+C（SIGINT）で行う（NFR-6 の手動の確認）
