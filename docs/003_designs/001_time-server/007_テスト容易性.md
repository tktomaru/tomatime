## テスト容易性

テストは test-engineer が `test/**/*.test.ts` に書く（`.claude/rules/coding.md` の TT-1〜TT-6）。差し替えはすべて M-5 の `createTimeServer` の引数で行い、グローバルの `Date` や `process.stderr` を書き換えない。

| 差し替え点 | 差し替える方法 | テストで再現すること | 対応する受け入れ条件 |
|---|---|---|---|
| 時刻の取得元 | `createTimeServer({ clock, writeErrorLine })` の `clock` に、テストが作った関数を渡す。呼ばれた回数を数える関数で包む | 固定のエポックミリ秒（`Date.parse('2026-11-25T03:04:05.000Z')` のように作る。UTC の年が 0000 と 9999 の値も、4 桁の年の ISO 形式の文字列を `Date.parse` で読んで作れる）、呼ばれた順に値を変える列、`Error` と `Error` でない値の例外、`NaN`、`Infinity`、`-Infinity`、有効範囲の境界の値、呼び出しの回数 | FR-1-AC-1〜FR-1-AC-13, FR-2-AC-1〜FR-2-AC-5, FR-3-AC-1〜FR-3-AC-6, FR-4-AC-1〜FR-4-AC-17, FR-5-AC-1, FR-5-AC-3, FR-5-AC-4, FR-6-AC-1〜FR-6-AC-5, FR-10-AC-1〜FR-10-AC-5 |
| 500 の 1 行の書き込み先 | 同じく `writeErrorLine` に、渡された文字列を要求ごとに配列へためる関数を渡す。失敗の再現には呼ばれると例外を投げる関数を渡す | 1 行の完全一致（LF を含む）、200・405 で呼ばれないこと（0 文字）、書き込みが失敗しても 500 のままで次の要求が 200 になること | FR-4-AC-10〜FR-4-AC-17, FR-10-AC-3, FR-10-AC-4 |
| 待ち受け | `createTimeServer` は待ち受けない。テストが `server.listen(0, '127.0.0.1')` を呼び、`server.address()` の `port` を使う。`after` / `t.after` で `server.closeAllConnections()` と `server.close()` を呼ぶ | ポート 0 での起動、`fetch` による要求、`node:net` の `connect` による生の要求（FR-6-AC-2〜FR-6-AC-5） | FR-1〜FR-6、FR-10 の受け入れ条件 |
| タイムゾーン | 同じプロセスで `process.env.TZ` を `UTC`、`Asia/Tokyo`、`America/New_York` の順に代入する（Node.js は代入でタイムゾーンを切り替える）か、`TZ` を変えた子プロセスで確かめる。終わったら元の値に戻す | 同じ瞬間に同じ本文 | FR-1-AC-12 |
| 起動コマンド | `package.json` の `scripts.start`（`node src/main.ts`）と同じ引数で、`child_process.spawn(process.execPath, ['src/main.ts'], { cwd: <リポジトリ直下>, env })` を実行する。`env` に `TOMATIME_HOST`、`TOMATIME_PORT` を入れる・入れない・空文字列にする | 標準出力の `listening:` の行で待ち受けの開始を、プロセスの終了（`exit` イベント）で失敗を判定する（実時間を待たない。TT-5）。成功の場合はテストの最後にプロセスを止める | FR-7-AC-1〜FR-7-AC-15, FR-8-AC-1〜FR-8-AC-3 |
| リポジトリ直下のファイル | `README.md`、`Dockerfile`、`package.json` を `fs.readFileSync` で読む | 節の切り出し（`## ` 見出しの範囲）、命令の行の切り出し、文字列と正規表現の検査 | FR-9-AC-1〜FR-9-AC-3, FR-11-AC-1〜FR-11-AC-5, FR-12-AC-1, FR-12-AC-2 |

### テストの補足

- 換算・整形・応答の作成での例外（`internal`）は取得元の差し替えだけでは起こせないため、テストにしない。コードレビューで 5 章の構造（1 つの `try` と `fail`）を確かめる（要件定義書の FR-4 の補足）
- `FR-7-AC-1` はポート 3000 を使う。開発機でポート 3000 が使われている場合は失敗する（要件定義書の受け入れ条件の補足）
- `FR-7-AC-9` と `FR-7-AC-13` は子プロセスの環境変数に空文字列を渡す。Windows でも環境ブロックに `NAME=` の形で空の値が渡る前提で、子プロセスの `process.env` で空文字列になることを test-engineer がテストの中で確かめる（テストが成功した場合はこの前提が成り立っている）
- `FR-7-AC-14` は IPv6 のループバックが使えない場合、理由を示して `t.skip` してよい（要件定義書の受け入れ条件の補足）
- `fetch` は既定で接続を再利用するため、`server.close()` だけでは閉じ終わらないことがある。`server.closeAllConnections()` を先に呼ぶ
- `HEAD` の本文の長さは `(await res.arrayBuffer()).byteLength` が 0 であることで確かめる（要件定義書の受け入れ条件の補足）

### 受け入れ条件 ID のない検証（NFR）

非機能要件には受け入れ条件 ID を振らない（`.claude/rules/documents.md` の 3 章）。TT-2 は受け入れ条件 ID をテスト名の先頭に入れる決まりで、NFR を確かめるテストの名前の決まりを持たない。本書では、NFR をテストで確かめる場合はテスト名の先頭に NFR の ID を入れる（例: `test('NFR-5: …', ...)`）ことにする（AI が決定。11 章の U-1）。

| 要件 | テストで確かめること（テスト名の先頭） | コードレビューで確かめること |
|---|---|---|
| NFR-1 | 受け入れ条件 FR-1-AC-10、FR-1-AC-11、FR-4-AC-7、FR-10-AC-1 と、各受け入れ条件のヘッダーの確認で足りる。NFR-1 の名前のテストは作らない | 3 章「状態を持たない」の決まり。M-4 が `Cache-Control: no-store` を 200・405・500 に付け、`ETag`、`Last-Modified`、`Expires` を付けないこと |
| NFR-2 | 受け入れ条件 FR-1-AC-12 | 3 章「タイムゾーン」の決まり（M-2 が UTC の getter だけを使う） |
| NFR-3 | 上の表の差し替え点を使う受け入れ条件 | M-1〜M-6 が `process` に触れないこと |
| NFR-4 | `npm run typecheck` と `npm test` の成功 | `package.json` の `dependencies` が空のオブジェクト、`engines.node` が `>=24` |
| NFR-5 | `NFR-5:` で始まる 1 件。`X-Forwarded-For: 203.0.113.1`、`X-Forwarded-Proto: https`、`X-Real-IP: 203.0.113.1` を付けた `GET /` と付けない `GET /` を、同じ固定時刻（UTC `2026-11-25T03:04:05.000Z`）を返す取得元で送り、ステータス、本文、`Content-Type`、`Cache-Control` が一致すること | M-4 が `req.method` 以外の要求の情報を読まないこと。TLS、認証、レート制限、接続元による制限の処理がないこと |
| NFR-6 | なし（手動の確認） | M-7 が SIGINT・SIGTERM で `process.exit(0)` を呼ぶこと、`server.close()` を待たないこと、常駐化の処理と終了時に応答を作る処理がないこと |
| NFR-7 | なし | M-1 が `Date.now()` だけを使うこと。外部へ接続する API（`fetch`、`net.connect`、`node:dgram`、`node:dns`）を `src/` で使わないこと |
| NFR-8 | なし（利用者の手動の確認。要件定義書の NFR-8 の補足） | - |

- NFR-5 をテストとコードレビューの両方で確かめるのは、要件定義書の NFR-5 の検証方法（「テストで確かめる。コードレビュー」）に従うため。要件定義書は変更しない
- 本番で 1 行の書き込み先が `process.stderr` になっていること（M-7 の起動手順 3）は、コードレビューと NFR-8 の手動の確認で確かめる（要件定義書の受け入れ条件の補足）
- FR-6 の 408（受信の時間切れ）はテストにせず、コードレビューで `headersTimeout`、`requestTimeout`、`timeout`、`keepAliveTimeout` を設定していないことを確かめる（要件定義書の FR-6 の補足）
