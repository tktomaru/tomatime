## 検討した代替案

いずれも AI（software-designer）が要件定義書の範囲内で選んだ。

| 論点 | 採用した案 | 採用しなかった案 | 理由 |
|---|---|---|---|
| TypeScript の実行方法 | 型ストリップで `.ts` を直接実行（`node src/main.ts`） | `tsc` で `dist/` に変換して実行する。`tsx` を使う | 変換の工程がなく、`Dockerfile` の `CMD` と `scripts.start` が同じ 1 つのコマンドになる（FR-11-AC-3）。`tsx` は依存が増える（NFR-4、`.claude/rules/coding.md` の 1 章）。Node.js 24 以上では型ストリップが既定で使える |
| 時刻の取得元の差し替え | `createTimeServer` の引数 `clock` | `node:test` の `mock.timers` で `Date` を差し替える。モジュールの変数を書き換える | 引数なら例外・`NaN`・呼ばれた順の値を素直に注入でき、テストどうしが干渉しない（CD-1、TS-6）。グローバルの差し替えは Node.js 内部の `Date` の利用（`Date` ヘッダー）にも及ぶ |
| 500 の 1 行の書き込み先 | `createTimeServer` の引数 `writeErrorLine` | `process.stderr.write` をテストで書き換える。子プロセスの標準エラー出力を読む | 引数なら要求ごとの 1 行と書き込みの失敗を同じプロセスで確かめられる（NFR-3、FR-4-AC-16） |
| 失敗の表し方 | 取得元の例外・戻り値の異常は戻り値（`FormatResult`、`TimeFailure`）で表し、想定外の例外だけ外側の `catch` で受ける | すべてを例外にして 1 つの `catch` で原因を判定する | 原因の文言（`source threw` / `source returned ...` / `internal error`）を例外の種類の推定なしに決められる。取得元の例外を専用の `try` で受けるので、取得元の例外が `internal` に混ざらない |
| 応答の作り方 | 内容（ステータス、ヘッダー、本文）を組み立ててから `writeHead` と `end` を 1 回ずつ呼ぶ | `setHeader` を順に呼び、`write` で本文を送る | 送信の前の例外では何も送られていないことが構造で保証され、500 に切り替えられる（TS-5） |
| 500 の `Date` を付けない方法 | `res.sendDate = false` | `res.removeHeader('Date')` | Node.js の `Date` は `writeHead` の時点で `sendDate` を見て付けるもので、`removeHeader` では消えない |
| 有効範囲の判定 | 日本時間の秒の数値を定数の境界と比べてから `Date` を作る | `new Date()` を作って `getTime()` が `NaN` かで判定する | `Date` の範囲（±8.64 × 10^15 ms）と本文の年 4 桁の範囲（FR-4）は異なる。`Date.UTC` は年 0〜99 を 1900 年代として扱うため使わない |
| 停止の方法 | シグナルで `process.exit(0)` | `server.close()` で処理中の要求を待ってから終了 | NFR-6 が処理中の要求の完了を待たないとしている。`close` は keep-alive の接続で終了が遅れ、`docker stop` の猶予（10 秒）を超えうる（NFR-8） |
| 起動失敗の終了 | `process.exitCode = 1` にして自然に終了 | `process.exit(1)` | パイプへの標準エラー出力の書き込みが非同期の環境で、`process.exit` は書き込み前に終了しうる。FR-7、FR-8 の受け入れ条件は標準エラー出力の行を確かめる |
| 基盤のイメージ | `node:24-slim` | `node:24`、`node:24-alpine` | `slim` は Debian 系で `node:24` より小さい。`alpine` は C ライブラリが musl で、利用者の VPS（Debian）と系統が異なる。いずれも FR-11-AC-1 の正規表現に一致する |
| モジュールの分け方 | 取得（M-1）、整形（M-2）、失敗の 1 行（M-3）、応答（M-4）、サーバー生成（M-5）、設定（M-6）、入口（M-7）の 7 つ | 1 つのファイルにまとめる | 取得・整形・応答を分ける決まり（`.claude/rules/time-safety.md` の 2 章）と、入口だけが `process` に触れる構成（CD-2、NFR-3）を、ファイルの境界で確かめられる |
| NFR-5 の検証 | `NFR-5:` で始まるテスト 1 件とコードレビュー | コードレビューだけにする | 要件定義書の NFR-5 の検証方法が「テストで確かめる」を含むため、要件定義書を変えずに従う。TT-2 は受け入れ条件 ID の決まりで、NFR の ID をテスト名に入れることを妨げない（11 章の U-1） |
