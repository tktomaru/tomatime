重大・高・中の指摘はない。依頼で特に見てほしいとされた点の確認結果は次のとおり。

- TS-5 / CD-4（`internal`）: `src/handler.ts:112-127` は設計書 5 章の骨格と同じ構造になっている。405 の組み立て、取得（`readAndFormat` の中の専用の `try`）、`formatJst`、`plan200`、`send` が 1 つの `try` の中にあり、`catch` は `fail` で 500 を返すか、`res.destroy()` で切断する。`fail` の本文とヘッダーは固定の定数だけで作られ、例外の内容、取得元の値、時刻は入らない。`sendDate=false` なので `Date` も付かない。送信の前に応答の内容を組み立て終えるため、`writeHead` の前の例外では何も送られておらず、`writeHead` の後の例外では `headersSent` が真になって切断する。`setHeader` を使っていないので、200 のヘッダーが 500 に混ざることもない。`failureLine` の中の例外（`name` の getter など）と書き込み先の例外は、それぞれ専用の `try` で捨てられる。`formatJst` は正規表現 `TEXT_PATTERN` に合わない文字列を本文にせず、例外にする（`src/format.ts:43-46`）。時刻の形式の値や時刻らしい値を返す経路は見つからなかった。
- TS-2 / NFR-1: どのモジュールにも、時刻・本文・応答を保持する変数はない（モジュールの定数は固定の文字列と境界の数値だけ）。1 回の要求で `clock()` を 1 回呼ぶ。`Cache-Control: no-store` を 200、405、500 のすべて（HEAD を含む）に付けており、`ETag`、`Last-Modified`、`Expires` は付けていない。`Transfer-Encoding: chunked` にもならない。
- TS-4 / NFR-2: 日本時間は `epochMs + 32_400_000` を `Math.floor` で秒に切り捨て、`new Date(number)` を UTC の getter で読んで求めている。境界の定数 `MIN_JST_MS=-62135596800000`（0001-01-01T00:00:00）と `MAX_JST_MS=253402300799000`（9999-12-31T23:59:59）は正しい値。負の値も `Math.floor` で以前の秒に丸まる。`Dockerfile` に `TZ` と `/etc/localtime` はない。
- FR-4 の 1 行: `src/failure.ts` の文言、CR・LF の置き換え（`/[\r\n]/g` を `' '` に置換）、LF 1 つで終わる点は、インターフェース仕様と文字単位で一致している。本番の書き込み先は `src/main.ts:29-31` の `process.stderr.write(line)`。1 件の 500 につき 1 回だけ呼ばれ、200 と 405 では呼ばれない。
- NFR-6: `process.once('SIGINT'/'SIGTERM', () => process.exit(0))`（`src/main.ts:35-39`）でハンドラを明示的に登録しているので、PID 1 でも既定のシグナルの扱いに頼らずに止まる。`Dockerfile` の `CMD ["node", "src/main.ts"]` は exec 形式で、`ENTRYPOINT` はない。`server.close()` を待たず、終了時に応答を作る処理もない。コンテナ内で実際に止まるかは NFR-8（手動確認）による。
- NFR-5: `src/handler.ts` が読む要求の情報は `req.method` だけ（URL、ヘッダー、本文は読まない）。TLS、認証、レート制限、接続元による制限の処理はない。テスト `NFR-5:` も成功した。
- NFR-7: 外部へ接続する API（`fetch`、`net.connect`、`dgram`、`dns`）は `src/` で使っていない。`node:net` は `isIP` だけを使っている。
- TT-5 / TT-3: テストに `setTimeout` での待ちはない。待ち受けの開始は `listening:` の行、失敗は子プロセスの `close` で判定している。ポート 0 で立てた server は `t.after` で `closeAllConnections()` してから `close()` し、子プロセスは `t.after` で `kill()` して `close` を待つ。`childSeesEnv` の子プロセスは自分で終了する。
- 設計書 U-3（待ち受けの開始後に server が出す `error`）: Node.js の `net` は accept の失敗（EMFILE など）で server に `error` を出す。登録された処理がないため、プロセスは捕捉されない例外で終了する。処理中の接続は応答なしで切れるだけで、時刻の形式の値・前回の値・既定値を返す経路はない。TS-1〜TS-6 には影響しないと判断した。終了後に再起動されるかどうか（可用性）は、常駐・自動起動をスコープ外とした要件の範囲で、受け入れたリスク「Node サーバーの停止中」に含まれる。
- Node.js が 200 と 405 に付ける `Date` ヘッダーは、要件で値を規定しない既定の動作（インターフェース仕様の「応答ヘッダー」）。値は OS の時計から作られ、1 秒単位で更新されるので、TS-3 の「古い時刻」には当たらないと判断した。
