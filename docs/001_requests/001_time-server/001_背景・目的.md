## 背景・目的

### ミッション・ビジョン

ミッションは、生成 AI が作業中に現在時刻を知る手段を用意することである。依頼の原文は「時刻サーバーを実現したい。生成AIが時刻を取得できないので、httpで取得して参照するように指示したい。」（/request-intake の引数、2026-11-24）。

ビジョンは、利用者が生成 AI に「この URL から現在時刻を取得して参照する」と指示すれば、生成 AI が全世界に公開されたサーバーへ HTTPS で GET 要求し、日本時間の現在時刻を本文で受け取り、その値を参考の現在時刻として使える状態である（公開サーバーと HTTPS: D-4、日本時間: D-2、Web 取得ツールは Claude Code の WebFetch: D-3、D-11）。公開と HTTPS は利用者が契約している VPS（ConoHa、Debian）の nginx が担い、今回作る Node サーバーは VPS 上の Docker コンテナ内で動き、nginx から HTTP で要求を受ける（D-4、D-7、D-18、D-22）。成果物には、Node サーバーを動かす Dockerfile（D-25）と、利用者が生成 AI に指示しやすいよう指示文の例（D-17）も含める。企画書はない。

### 現状と困りごと

依頼の原文では「生成AIが時刻を取得できない」とされている。生成 AI は自分では現在時刻を知る手段を持たないため、日時に関わる作業（例: 日付の記入、経過時間の判断）で正しい現在時刻を前提にできない。頻度や、誤った時刻による具体的な影響は依頼文に記載がなく、確認していない。

依頼の原文には「MCPにするほどでもないかと思った」とある。これは、MCP サーバーを作るより簡単な HTTP での取得を望む意向の表明として扱う（AI の解釈）。質問 A への回答（D-4）で HTTP サーバーとして作る方針が示され、MCP は対象外になった。

### 解決したい問題

望ましい状態は、生成 AI が必要なときに OS の時計の値に基づく現在時刻を取得できることである。現状との差は、生成 AI から呼び出せる時刻の取得手段がないことにある。

メインのセッションの動作確認（2026-11-24）で、Claude Code の WebFetch は `http://127.0.0.1` を取得できなかった（HTTPS に変換され、サーバーに要求が届かなかった。C-8）。このため、同じマシンの平文 HTTP サーバーを Web 取得ツールで読む方法は成り立たない。利用者は VPS の nginx で HTTPS を受け、HTTP に変換して Node サーバーへ渡す構成を示した（D-4）。

また WebFetch は同じ URL の結果を 15 分ほど保持するとされる（C-8）。保持された古い時刻を受け取らないよう、生成 AI に毎回異なる URL で呼ばせる（D-6）。クエリのない要求にも時刻を返すため（D-9）、付け忘れによる古さは指示文の例で防ぐ（D-17）。

### 目的と成功の目安

**経営ニーズの観点**　個人の開発補助ツールであり、経営上の成果や投資判断は関係しない（依頼文に記載がなく、AI の解釈）。期待する効果は、生成 AI に時刻を参照させる手間を、簡単な指示で済ませられることである。

**業務ニーズの観点**　利用者が生成 AI に作業させるとき、生成 AI が現在時刻を推測せず、サーバーから取得した値を参考の現在時刻として使うように変える（依頼原文「httpで取得して参照するように指示したい」）。運用者は Node サーバーを Docker 内で動かし、時刻を返せなかったときは原因を標準エラー出力で確かめる（D-22、D-23）。

**成功の目安**　次の状態を確認できれば目的を達成したと言える（AI の解釈・提案。人のレビューで確認する）。

- 生成 AI が WebFetch で公開 URL を HTTPS で取得し、nginx を経て Docker 内の Node サーバーが返す、その時点の OS の時計に基づく日本時間の時刻を `YYYY-MM-DD HH:mm:ss` の形式で受け取れる（REQ-1、REQ-2、REQ-4、REQ-15）
- 時刻を取得・整形できないとき、時刻の形式の値を受け取らず、運用者が原因を標準エラー出力で確かめられる（REQ-3、REQ-14）
- 毎回異なるクエリ文字列を付けて呼べば、2 回目以降もその時点の時刻を受け取れる（REQ-7、REQ-11、D-6）

成功の目安は、公開後に実際の WebFetch で確かめる。そのとき、[C-8 の補足](007_制約.md#c-8-の補足)の「未確認の前提」3 点（クエリ文字列を区別した保持、本文の書き換えの有無、5xx 応答の本文が渡るか）も確かめる。
