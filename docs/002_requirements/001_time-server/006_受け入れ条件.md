## 受け入れ条件

各 FR に、正常系と異常系を 1 件以上書く。Then には観測できる結果（ステータス、ヘッダー、本文の完全一致）を書く。

時刻は、時刻の取得元に固定値を注入して確かめる（NFR-3）。Given の UTC の値は ISO 8601 の文字列で示し、取得元がその瞬間のエポックからのミリ秒の数値（FR-1 の補足）を返すことを表す。FR-1〜FR-6、FR-10 は、テストからポート 0 で起動したサーバーに要求を送る。FR-7、FR-8 は `package.json` の `start` スクリプトと同じコマンドを子プロセスで直接実行して確かめる（FR-7 の補足）。FR-9、FR-11、FR-12 は、リポジトリ直下のファイルの文字列を読んで確かめる。

Then の中の次の語は、それぞれ次の内容を表す（[インターフェース仕様](004_インターフェース仕様.md)の「応答ヘッダー」「ログ・標準出力・標準エラー出力」「Dockerfile」）。

### 受け入れ条件の補足

- FR-1-AC-10、FR-1-AC-11、FR-4-AC-7、FR-4-AC-8、FR-4-AC-16 の「1 回目」「2 回目」は、時刻の取得元が呼ばれた順を指す
- FR-4-AC-10〜FR-4-AC-17、FR-10-AC-3、FR-10-AC-4 の「書き込まれた 1 行」は、NFR-3 で差し替えた書き込み先で確かめる。本番で書き込み先が標準エラー出力（`process.stderr`）になっていることは、コードレビューと NFR-8 の手動確認で確かめる
- FR-4-AC-16 は、書き込みが失敗しても 500 の応答が変わらず、プロセスが後の要求に応えることを確かめる（FR-4 の補足）
- FR-10 の「本文が 0 バイト」は、`fetch` で受け取った応答の本文の長さで確かめる。`Content-Length` は本文の長さではなく、同じ条件の `GET` の本文の長さを示す（FR-10 の補足）
- FR-11-AC-1 と FR-11-AC-4 の正規表現の中の `\|` は、表のセルの書き方による `|` の表記で、正規表現としては `|` を表す
- FR-11、FR-12 は Docker を使わずにファイルを読んで確かめる。イメージの作成とコンテナでの動作は NFR-8（利用者の手動確認）で確かめる
- FR-11-AC-1 の正規表現は、タグの先頭が 24〜99 の版の番号で、その後ろが終わりか `.` か `-` で続くこと（例: `node:24`、`node:24-slim`、`node:24.11.0-trixie-slim`）を表す。`FROM` の後ろの `AS <名前>` は多段の作成のために許す
- FR-11-AC-3 は、`scripts.start` がシェルの機能（`&&`、変数の展開、引用符）を使わず、半角空白で区切った引数だけからなることを前提にする（FR-7 の受け入れ条件でも同じコマンドを子プロセスで直接実行するため）
- FR-1-AC-12 は、同じプロセスの中で環境変数 `TZ` を切り替えるか、`TZ` を変えた子プロセスで確かめる。開発機（Windows 11）と VPS（Debian）の両方での確認は U-3
- FR-6-AC-2〜FR-6-AC-5 は、`fetch` では送れない要求のため、TCP の接続で送り、受信したバイト列を確かめる。FR-6 の 408 は受け入れ条件にしない（FR-6 の補足）
- FR-4 の換算・整形・応答の作成での例外は受け入れ条件にせず、コードレビューで確かめる（FR-4 の補足）。FR-5 の `CONNECT` も受け入れ条件にしない（FR-5 の補足）
- FR-7-AC-14 は、テストを実行するマシンで IPv6 のループバックが使えない場合、その理由を示してテストを飛ばしてよい
- FR-7、FR-8 の受け入れ条件は実時間を待たない。待ち受けの開始は標準出力の `listening:` の行で、失敗はプロセスの終了で判定する
- FR-7-AC-1 は既定のポート 3000（D-21）に依存する
- FR-7-AC-15 は、コンテナで `Dockerfile` の `ENV` により指定する 0.0.0.0（FR-11）で待ち受けられることを、Docker を使わずに確かめる
- FR-8-AC-3 の `192.0.2.1` は文書用に予約されたアドレス（RFC 5737 の TEST-NET-1）で、通常のマシンには割り当てられていない
