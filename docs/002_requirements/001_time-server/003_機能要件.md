### FR-n の補足

- FR-1: 「その時点」は、要求を受けて応答を作るときに時刻の取得元から取得した瞬間を指す（C-5、要求書の REQ-1 の補足）。1 回の要求につき取得元を 1 回だけ呼ぶ
- FR-1: 日本時間は、取得した瞬間（UTC 基準）に 9 時間を足して求める。OS とコンテナのタイムゾーン設定（環境変数 `TZ`、`/etc/localtime` を含む）を使わない（D-2、C-6、C-11、NFR-2）
- FR-1: 秒未満は切り捨てる（その瞬間以前で最も近い秒にする）。四捨五入では OS の時計がまだ達していない秒を返すことがあり、OS の時計から取得した値と異なる時刻になる（C-4）ため、要求書の申し送りの提案どおり切り捨てを AI が決定した
- FR-1: ステータス 200 は HTTP の成功を示す値で、要求書の申し送りの提案（AI の提案）を AI が決定した
- FR-1: 時刻の取得元は、呼ぶたびに現在の瞬間を UTC 基準のエポック（1970-01-01T00:00:00Z）からのミリ秒の数値で返す。本番では OS の時計（Node.js の `Date.now()` と同じ値。コンテナ内ではコンテナから見える OS の時計、C-11）を使い、テストでは差し替える（NFR-3）。戻り値を数値に決めたのは、受け入れ条件で注入する値（固定値、`NaN`、`Infinity`）を一意にするためで、AI が決定した（適用中）
- FR-2: パスは要求行の request-target のうちクエリより前の部分を指す。パーセントエンコードの解釈をしないため、不正なエンコード（例: `/%ZZ`）でも FR-1 と同じ応答になる
- FR-3: 空のクエリ（`?` だけ、`?t=`）、同じ名前の複数指定（`?t=a&t=b`）、`t` 以外の名前、不正なエンコードを含め、クエリ文字列は読まない。長さの上限は FR-6 の上限による
- FR-4: 判定の対象は次のとおり。いずれも FR-4 の応答にする
  - 時刻の取得元が例外を投げる
  - 時刻の取得元が有限の数でない値（`NaN`、`Infinity`、`-Infinity`）を返す
  - 取得した瞬間の日本時間が `0001-01-01 00:00:00` より前、または `9999-12-31 23:59:59` より後（年が 4 桁の `0001`〜`9999` に収まらない値と紀元前の値）
  - 日本時間への換算、整形、応答の作成（本文を送る前）で例外が起きる
- FR-4: 有効範囲は、本文の年が 4 桁の形式に収まり、紀元前を表さない範囲として AI が決定した（要求書の申し送り「不正な時刻の値」）
- FR-4: 前回の応答で使った値、推定値、既定値で補わない（C-7）。次の要求では改めて取得元を呼ぶ
- FR-4: 取得元の例外と戻り値の異常は受け入れ条件で注入して確かめる（FR-4-AC-1、FR-4-AC-2、FR-4-AC-9）。換算・整形・応答の作成での例外は取得元の差し替えだけでは起こせないため、受け入れ条件にしない。設計では、時刻の取得から本文の送信までを 1 つの例外処理で囲み、どこで例外が起きても FR-4 の応答にする構成とし、コードレビューで確かめる（設計への申し送り）
- FR-4: `Date` ヘッダーは HTTP の日付で、時刻らしい値（要求書の用語集）に当たる。RFC 9110 の 6.6.1 は 5xx の応答で `Date` を付けなくてよいとしているため、Node サーバーの 500 には付けない（AI が決定）。200 と 405 は Node.js の既定どおり付き、本要件では値を規定しない
- FR-4: nginx はプロキシとして自分の `Date` を付ける（既定では上流の `Date` を置き換える）ため、生成 AI が nginx 経由で受け取る 500 には `Date` が付く。nginx の `Date` は VPS の OS の時計の値で、OS の時計から取得した値と異なる時刻には当たらない。`Date` を付けない要件の範囲は Node サーバーが返す応答までとする（D-7）
- FR-4: 標準エラー出力の 1 行は、500 の応答 1 件につき 1 行だけ出す。200 と 405 の応答、FR-6 の既定のエラー応答では出さない。1 行の形式と `<原因>` の文言は[インターフェース仕様](004_インターフェース仕様.md)の「ログ・標準出力・標準エラー出力」による（AI が決定）
- FR-4: 1 行に、発生時刻（タイムスタンプ）と、時刻の取得元が返した値（エポックからのミリ秒の数値）を含めない。理由は次のとおり（AI が決定、適用中）
  - 500 は時刻の取得・整形に失敗した経路で、別の経路で取得した時刻を書くと、失敗した取得元と異なる時刻の出どころが生まれる（`.claude/rules/time-safety.md` の TS-5 の趣旨。TS-5 自体は応答に対する原則）
  - 取得元が返した範囲外の値は時刻らしい値（要求書の用語集）で、誤った時刻であることが分かっている
  - コンテナのログには Docker が受け取った時刻を付けて表示できる（`docker logs --timestamps`。AI の知識で、NFR-8 の手動確認で確かめる）
- FR-4: 例外のメッセージ（`<message>`）は、原因を確かめるために変えずに含める（改行の置き換えだけを行う）。メッセージに日時の文字列が含まれる場合もそのまま出るが、標準エラー出力は運用者が読むもので、応答には入らない。応答（ステータス、ヘッダー、本文）は FR-4 の表のとおりで、標準エラー出力の内容によって変わらない
- FR-4: 標準エラー出力への書き込みが例外を投げても、応答は FR-4 のとおり（500、`time unavailable`）で、プロセスは後の要求の処理を続ける（AI が決定。要求書の申し送り「出力に失敗しても応答が時刻の形式にならないこと」）。この場合の 1 行は出なくてよい
- FR-5: 判定の順は、FR-6（Node.js が要求を受け付けない）、FR-5（メソッドが GET と HEAD 以外）、FR-4（時刻の取得・整形の失敗。HEAD は FR-10）、FR-1（HEAD は FR-10）の順。FR-5 に当たる要求では時刻の取得元を呼ばないため、取得元が例外を投げる状態でも 405 になる
- FR-5: `Allow` の値を `GET, HEAD` にするのは、RFC 9110 の 10.2.1 が `Allow` に対象のリソースが受け付けるメソッドを並べるとしており、D-20 で HEAD を受け付けることになったため（AI が決定）
- FR-5: `CONNECT` は Node.js の既定どおり応答を返さずに接続を閉じる（`connect` イベントを扱わない）。nginx は `CONNECT` を上流へ転送しないため生成 AI の経路では起きず、時刻を返す処理も通らないので、受け入れ条件では検証しない
- FR-5: 前の版で HEAD を 405 にしていた受け入れ条件（FR-5 の 2 番目）は、D-20 により削除した。番号は再利用せず欠番とする
- FR-6: Node.js 24 の既定の上限は 16 KiB（`--max-http-header-size` の既定値 16384 バイト）。HTTP/1.1 で `Host` がない要求は 400（`requireHostHeader` の既定 true）、受信の時間切れ（`headersTimeout`、`requestTimeout` の既定値）は 408、`Expect` が `100-continue` 以外は 417 になる。上限、時間切れ、`clientError` と `checkExpectation` の既定の扱いを変えない
- FR-6: 408 は既定の時間切れ（`headersTimeout` は 60 秒）まで待たないと起こせず、実時間を待たない決まり（`.claude/rules/coding.md` の TT-5）と両立しないため、受け入れ条件にしない。コードレビューで時間切れの設定を変えていないことを確かめる
- FR-7: 環境変数の妥当な値と既定値の使われ方は[インターフェース仕様](004_インターフェース仕様.md)の「環境変数」による。未設定のときだけ既定値を使い、空文字列を設定したときは妥当でない値として扱う
- FR-7: 検査の順は `TOMATIME_HOST`、`TOMATIME_PORT` の順で、最初に妥当でないと分かった 1 つだけを出力する
- FR-7: 「起動コマンド」は `npm start` を指す。受け入れ条件では、`package.json` の `start` スクリプトと同じコマンドを子プロセスで直接実行して確かめる（npm の出力が混ざらず、終了コードをそのまま観測できるため。AI が決定）
