# 要件定義（パイプライン 2 / 3）

## 1. 位置づけ

承認済みの要求 → 要件定義 → AI 一次レビュー 1 回 → 指摘の反映 → 人のレビュー → 実装テスト。[エージェントの共通ルール](../../rules/agents.md) に従う。

## 2. 入力

承認済みの要求書、機能名と文書のパス、ユーザーの回答・修正指示・選択の原文を使う。作成は `requirements`、人のレビュー後の更新は `requirements_review` で行う。

## 3. 出力

要件定義書は `docs/002_requirements/<NNN>_<機能名>/` に置く。AI 一次レビューの結果と未決事項を人のレビューで示し、`requirements_review` で承認を待つ。

## 4. 使うエージェント

requirements-engineer が文書を作成・更新し、requirements-reviewer が読み取り専用でレビューする。メインのセッションは進行とユーザーへの確認を担当する。

時刻の返却を扱う委任には、[返却形式を扱う作業の委任](../../rules/agents.md#返却形式を扱う作業の委任) の指示を含める。

## 5. 手順

`node .claude/harness/pipeline.mjs status` と会話の進捗を確認し、**該当する行の手順だけを開く**。分岐先とナレッジは必要になった時点で読む。`request_review` は要求書の承認待ち。他のフェーズはそれぞれのスキルで進める。

| いまの状況 | 開く手順 |
|---|---|
| `requirements` で初稿を作成する | [要件定義書の作成](002_workflow/001_要件定義書の作成.md) |
| 初稿がそろった、または一次レビュー結果の処理を再開する | [AI 一次レビュー](002_workflow/002_AI一次レビュー.md) |
| 指摘や人の回答を反映し、要件定義書をユーザーに提示する | [人のレビュー依頼](002_workflow/003_人のレビュー依頼.md) |

## 6. レビュー後・例外時

| いまの状況 | 開く手順 |
|---|---|
| 人のレビューへの回答・修正指示を受けた、または差し戻しから要件定義を再開する | [回答・修正指示の反映](002_workflow/005_回答・修正指示の反映.md) |
| 承認済みの要求そのものを変える必要がある | [要求への差し戻し](002_workflow/006_要求への差し戻し.md) |
| フックから要件定義書の承認を記録したと通知された | [承認後の引き継ぎ](002_workflow/007_承認後の引き継ぎ.md) |

ハーネスに拒否されたら、その理由に従って対応する。
