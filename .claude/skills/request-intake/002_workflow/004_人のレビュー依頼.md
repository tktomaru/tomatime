## 人のレビュー依頼

要求書の初稿にレビューの指摘を反映したとき、または人の回答を文書に反映したときに読む。

1. 要求の確定に必要な重要事項が未回答なら [重要事項の確認](002_重要事項の確認.md) を優先する。回答を得たら request-analyst に渡し、要求書への反映後にこの手順を続ける。
2. フェーズが `request` なら `node .claude/harness/pipeline.mjs advance` で `request_review` に進める。形式検査が NG なら理由を request-analyst に渡し、該当箇所の修正後に `advance` を再実行する。
3. 要求書のパスと次の内容を示す。ユーザーの判断をまだ聞いていない指摘が残っている場合は、同じレビュー依頼の中で [残った指摘への対応](005_残った指摘への対応.md) に従う。
4. ユーザーに人のレビューを依頼してターンを終える。レビューへの回答は [回答・差し戻しの反映](006_回答・差し戻しの反映.md)、承認通知は [承認後の引き継ぎ](007_承認後の引き継ぎ.md) で扱う。

| 項目 | 伝える内容 |
|---|---|
| 文書 | 要求書のパス |
| 重大・高の指摘 | 該当する残った指摘とその理由を先頭に示す |
| 確認してほしい前提 | 目的と成功の目安、対象範囲、主な利用者を示す。採否に影響する管理指標、データ検証結果、ツールの条件があれば添える |
| 要求一覧と決定の根拠 | REQ-n、要求の要約、根拠区分、決定主体・状態、解釈。新しい D-n・C-n の原文や資料の参照先 |
| 未回答の確認事項 | Q-n、論点、選択肢、推奨、推測で決めた場合のリスクを、決めるべき順で示す。回答済みの事項は決定事項を参照する |
| AI 一次レビューの結果 | レビュー時点の判定、主な修正、残った指摘、確認できなかった観点、ユーザーが選んだ対応。残った指摘がなければ「残っている指摘なし」 |
| プロセス質問 | 確認の漏れや相談すべき相手を見つけるための質問を 1〜2 問添える。必要なら [ヒアリング](../001_request-definition/004_ヒアリング.md) を参照する |
| 依頼 | 内容でよければ「承認」とだけ返信してもらう。修正指示と確認事項への返信も受け付ける。次工程へ申し送る論点は、推奨案と未決事項としての扱いを伝える |
