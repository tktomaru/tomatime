## 要求定義の 11 プロセス

初稿を作るときはプロセス 1 から 11 まで順に進める。前の結果を次の判断の根拠にする。各プロセスで得た事実と未決事項を作業中に整理し、プロセス 11 で要求書にまとめる。

| プロセス | 行うこと | 次へ渡す結果 |
|---|---|---|
| 1. 戦略と目的を確立する | 依頼と既存の合意から、関係するミッション・ビジョン、解決すべき問題、システムで達成したいことを確かめる | 目的と、成功したと判断できる状態の候補 |
| 2. スコープを設定する | 目的に照らし、対象の業務・利用場面、初版の範囲、対象外、他システムや人との境界を決める。利用者の業務視点で情報系ユースケースを描き、前提や結果が異なる複数のシナリオを整理する | 対象・対象外、境界、情報系ユースケース図とシナリオ |
| 3. 対象ユーザーを洗い出す | スコープごとに、直接の利用者、呼び出し元、結果を使う人、設置・運用者、判断や承認を担う人を確認する | ユーザー・関係者の一覧と役割、調査先 |
| 4. 現状を把握する | 現状の業務、情報の流れ、性能、実データ、例外や暗黙のルールを調査する。必要な調査方法だけを、ヒアリング、アンケート、ドキュメント調査、現地調査、マネジメント調査、データ・値の調査、ワークショップから選ぶ | 現状の事実と根拠、望ましい状態との差、確認済みのデータと未確認の点 |
| 5. 経営・業務・情報ニーズを洗い出す | 現状との差から、経営上達成したいこと、業務上変える行動や判断、そのために必要な情報を洗い出す。顕在化しにくいニーズは調査結果から候補を挙げる。投資判断が関係する場合は、期待する効果と、それが生まれる行動の変化を結び付ける | ニーズとその関連図、優先順位と根拠、期待する効果、機能要求の候補 |
| 6. CSF と管理指標を洗い出す | 目的とニーズから、成功に不可欠な要因（CSF）と、進捗や成果を確かめる管理指標を挙げる。複数の経営観点を対応付ける必要がある場合はバランス・スコアカードを使う | 成功要因、対応する指標、確認する判断や成果 |
| 7. 用語集・指標定義を作る | 関係者の間で意味がずれる用語と指標の定義をそろえる。指標には対象、算出方法、単位、測定期間、除外条件を記す | 用語集と指標の定義、解釈や適用範囲が未確定の事項 |
| 8. データの粒度をそろえる | 指標や出力に必要な粒度と、入手できるデータの粒度・精度・更新頻度・履歴を照合する。データの範囲、収集元、収集可能性を確かめ、欠損や異常値が利用に与える影響と必要なデータ加工を整理する | データ・ソース、必要な範囲と粒度、検出したエラー、データ加工要求 |
| 9. 非機能要求を洗い出す | 可用性、環境、セキュリティ、コンプライアンス、システム、運用、処理パフォーマンス、品質を、利用場面・データ・既存制約に照らして点検する | 根拠のある非機能要求・制約、未決事項、対象外の理由 |
| 10. アプリケーション・タイプを判定する | 利用者との接点、必要な処理、データ、非機能要求から、画面での業務処理、HTTP API、定期処理、分析・可視化など必要なアプリケーションのタイプを判断する。ツール選定に必要な条件をここで明確にする | アプリケーション・タイプと判断根拠、ツール要求・選定指針、未決事項 |
| 11. 要求書を作成する | 要求書テンプレートの README「要求書に含める内容」に沿って、1〜10 の結果を要求書に反映する。依頼文と回答、確認した事実、推測、合意の範囲を区別し、各項目を根拠までたどれるようにする | テンプレートに沿った要求書の初稿と必要な補足資料 |

目的・範囲・実現可能性などを左右する重要事項が見つかったら、そのプロセスから [重要事項の確認](002_重要事項の確認.md) に進む。中断した番号と回答に依存する判断を共有し、回答後はそのプロセスから続ける。回答や修正で前の前提が変わる場合は、影響を受ける最初のプロセスに戻り、関係する後続の結果を更新する。

小規模な依頼でも観点は順番に確認する。業務が存在しない、該当するデータがないといった場合は結果と理由を簡潔に残す。調査手法、図、スコアカード、調査資料の量は案件に合わせる。確認できていない判断は Q-n や要件定義への申し送りに残し、実績や目標値を推測で埋めない。補足が必要な段階で [ナレッジの目次](../001_request-definition/README.md) から該当する章を開く。

### プロセス 11 での反映先

| 要求書の章 | 反映するもの |
|---|---|
| 背景・目的 | ミッション・ビジョン、システムの目的、現状との差、CSF と管理指標（プロセス 1、4、6） |
| 利用者と利用場面 | ユーザー・関係者の一覧、業務の流れ、異常・例外時の場面（プロセス 3、4） |
| 要求一覧 | スコープ、ニーズとその関連図、指標 BOOK、アプリケーション・タイプとツール選定指針（プロセス 2、5、7、10） |
| 機能要求一覧・非機能要求一覧 | ニーズから導いた機能要求、非機能要求、根拠が確認できた潜在的な要求（プロセス 5、9） |
| 既存システムへの影響 | 現状調査の結果、既存システムへの影響、データ検証結果（プロセス 4、8） |
| 決定事項・制約・確認事項 | 人が明示した決定、適用する制約、未決事項と後工程で確かめる項目（全プロセス） |
| 補足資料 | ユーザーレビューに必要な企画書、調査資料、現地写真の添付・参照先（調査・文書化） |
| ユースケース | 業務視点の情報系ユースケース図と、通常・代替・例外などのシナリオ（プロセス 2） |
| 用語集 | 用語 BOOK、複数の要求に共通する用語とデータ項目の定義（プロセス 7、8） |

機能要求と非機能要求の REQ-n は通し番号にする。起草の最後に、根拠と決定主体・状態、ID と参照先、表の形式、記入例やコメントの除去を確認する。初稿をメインのセッションに渡し、AI 一次レビュー 1 回と指摘の反映を経てユーザーレビューへ進む。要求の確定に必要な重要事項を解消し、その版の承認がフックに記録されたら要求確定とする。
