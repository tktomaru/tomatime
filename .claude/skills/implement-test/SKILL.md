# 実装テスト（パイプライン 3 / 3）

## 1. 位置づけ

```
要求 → 人のレビュー → 要件定義 → 人のレビュー → [設計 → 実装 → テスト → レビュー]
```

あなた（メインのセッション）は進行役です。設計書は software-designer、本番コードは ts-developer、テストは test-engineer、レビューは code-reviewer に任せ、自分ではコードを書きません（例外はレビュー結果の保存 `docs/004_reviews/<NNN>_<機能名>/` だけ）。共通ルールは `.claude/rules/agents.md`（パイプライン CLI と承認の決まり）に従います。

## 2. 入力

### 2.1 開始の条件

| 条件 | 内容 |
|---|---|
| パイプラインのフェーズ | `implementation` |
| 要件定義書 | `docs/002_requirements/<NNN>_<機能名>/` が承認済み |

### 2.2 受け取るもの

| 項目 | 必須 | 入手元 |
|---|---|---|
| 機能名、文書のフォルダ | 必須 | `pipeline.mjs status`（「文書のフォルダ」のパスをそのままエージェントに渡す） |
| 要件定義書 | 必須 | `docs/002_requirements/<NNN>_<機能名>/` |

## 3. 出力

### 3.1 成果物

| 成果物 | 作成者 | フォーマット |
|---|---|---|
| `docs/003_designs/<NNN>_<機能名>/` | software-designer | `docs/900_templates/003_design/` |
| `src/`、`package.json`、`tsconfig.json` | ts-developer | `.claude/rules/coding.md` |
| `test/**/*.test.ts` | test-engineer | `.claude/rules/coding.md` の 4 章 |
| `docs/004_reviews/<NNN>_<機能名>/` | メインのセッション（code-reviewer の返却を見出しごとに章ファイルへそのまま保存） | `docs/900_templates/004_review/` |
| パイプラインのフェーズ `done` | `pipeline.mjs advance` | - |

### 3.2 ユーザーへの報告（完了報告）

| 項目 | 内容 |
|---|---|
| 文書 | 要求書・要件定義書・設計書・レビュー結果のパス |
| 実装した内容 | 要件 ID ごとの表 |
| 使い方 | 起動方法（`npm start`、ポート）、呼び出し例（`curl` と返却例） |
| テスト | 実行したコマンドと結果（件数） |
| 残っている指摘 | 中・軽微の指摘を表で |

## 4. 使うエージェント

| エージェント | 担当 | 渡すもの | 受け取るもの |
|---|---|---|---|
| software-designer | 設計書 | 機能名、依頼の種類（設計 / 設計の更新）、要件定義書・設計書のパス、担当する要件 ID、[アーキテクチャ設計の目次](001_software-architecture/001_architecture/README.md)、更新時は設計に関わる要確認事項・指摘（原文） | 作成・更新したファイル、実装への引き継ぎ、要確認事項 |
| ts-developer | 本番コード | 機能名、依頼の種類（実装 / 修正）、要件定義書・設計書のパス、担当する要件 ID、[実装の目次](001_software-architecture/002_implementation/README.md)、修正時は失敗出力・指摘（原文） | 変更したファイル、コマンドの結果、要確認事項 |
| test-engineer | テスト | 機能名、要件定義書・設計書のパス、対象の受け入れ条件、[テストの目次](001_software-architecture/003_test/README.md)、再実行時は修正内容 | 受け入れ条件との対応、実行結果、不具合、本番コードへの依頼 |
| code-reviewer | レビュー（読み取り専用） | 機能名、要件定義書・設計書のパス、追加・変更したすべてのファイル、2 回目以降は前回の指摘 | 指摘（重要度つき）、要件との対応の確認 |

書き込みを伴うエージェント（software-designer、ts-developer、test-engineer）は並行させない。

時刻の返却を扱う委任には、[返却形式を扱う作業の委任](../../rules/agents.md#返却形式を扱う作業の委任) の指示を含める。利用者向けの生成 AI 指示文や完了報告の返却例も、正本と承認済み要件に照らし合わせる。

## 5. 手順

[工程別の作業と参照先](001_software-architecture/README.md) に沿って、設計・実装・テストを委任するたびに担当の目次のパスを渡す。設計更新・実装修正・テスト再実行でも同じ目次を渡し、今回の変更に当てはまる章を番号順に参照するよう依頼する。

1. `status` を実行し、フェーズが `implementation` であることを確かめる
2. **設計**: software-designer に「設計」を依頼し、`docs/003_designs/<NNN>_<機能名>/` を書かせる。「要確認事項」で「止める」ものがあれば「6. レビュー後・例外時」に従う
3. **実装**: ts-developer に「実装」を依頼し、設計書のパスと software-designer の「実装への引き継ぎ」を渡す。担当する要件 ID は全 FR / NFR。要件が多ければ FR ごとに分けて順に依頼してよい。ts-developer の「要確認事項」に「設計の変更が必要」があれば、原文のまま software-designer に「設計の更新」として渡し、更新後に実装を再依頼する
4. **テスト**: test-engineer に、すべての受け入れ条件（FR-n-AC-m）をテストにして `npm test` を実行するよう依頼する
5. **修正のループ**: テストの失敗、「見つかった不具合」、「本番コードへの依頼」があれば、原文のまま ts-developer に「修正」として渡し（設計の変更を伴うものは先に software-designer に「設計の更新」として渡す）、test-engineer に再実行させる。3 回直しても通らなければ、状況をユーザーに報告して指示を仰ぐ
6. **レビュー**: code-reviewer を呼び、次の項目を今回の変更に応じて確かめるよう依頼する。返却を、`docs/900_templates/004_review/` に沿って見出しごとに `docs/004_reviews/<NNN>_<機能名>/` の章ファイルへそのまま保存する（再レビューでは上書きする）。

   - 想定した変更シナリオや障害経路をたどり、修正や影響が境界に収まるか確認する。変更箇所の依存方向と循環の有無を、呼び出し元・呼び出し先まで見る。
   - 境界の契約と品質要件を、テストや計測の結果と照合する。問題があれば、該当箇所、問題が起きる条件、修正案を既存のレビュー書式で返す。

7. 重大・高の指摘があれば、担当（設計書は software-designer、本番コードは ts-developer、テストは test-engineer）に直させ、手順 4 のテストと手順 6 のレビューをやり直す
8. `advance` を実行する。NG ならその理由に従って直す
9. 「3.2 ユーザーへの報告」を示す

## 6. レビュー後・例外時

| 状況 | 対応 |
|---|---|
| 要件定義書と食い違う・決めきれない点が出た（software-designer・ts-developer の「要確認事項」など） | `back requirements` で戻し、要件定義の [回答・修正指示の反映](../requirements-definition/002_workflow/005_回答・修正指示の反映.md) に従って承認を取り直す |
| 修正を 3 回繰り返しても通らない | 状況をユーザーに報告して指示を仰ぐ |
| ハーネスに拒否された | 理由に従って進め方を変える。回避策を探さない |
