# 時刻の安全に関するルール

tomaTime の呼び出し元は生成 AI で、返した文字列は参考の「現在時刻」として使われる。返す時刻は OS の時計の値で、OS の時計のずれは許容する（ユーザーの判断。参考時刻であり、ずれは重大な不具合につながらない）。一方で、**OS の時計から取得した値と異なる時刻を返すこと**（キャッシュされた古い値、タイムゾーンの取り違え、例外時の推定値・既定値）は防ぐ。すべての担当（要求、要件定義、設計、実装、テスト、レビュー）で、この点に関わる問題を重く扱う。

## 1. 原則

| ID | 原則 | 理由 |
|---|---|---|
| TS-1 | OS の時計の値を正確な時刻とみなす。同期状態の判定や外部 NTP への照会は行わない | 参考時刻であり、OS の時計のずれは許容する（ユーザーの判断） |
| TS-2 | 時刻を保持・再利用しない（応答のたびに取得する） | 古い時刻を返さないため |
| TS-3 | HTTP キャッシュ、プロキシ、サーバー内のキャッシュで古い時刻が返る余地を残さない | 同上 |
| TS-4 | タイムゾーンを一意に決める。暗黙に OS のタイムゾーンへ依存しない | 実行環境で結果が変わらないようにする |
| TS-5 | 時刻の取得・整形で例外が起きた経路では、[正本で定めた成功時の形式](../specs/time-response-format.md) の時刻や、時刻らしい値（推定値、前回値、既定値）を返さない | 想定外の状態で誤った時刻を返さないため |
| TS-6 | 時刻の取得元を差し替え可能にし、固定時刻と取得失敗（例外）をテストで再現する | 実時間に依存しない検証のため |

## 2. 担当ごとの確認観点

| 担当 | 確認すること |
|---|---|
| 要求（request-analyst） | 時刻を取得・整形できない場合（例外）の振る舞い、タイムゾーンと表記、エンドポイント・ステータス・Content-Type、キャッシュ、公開範囲が決まっていなければ確認事項にする |
| 要件定義（requirements-engineer / requirements-reviewer） | 成功時の本文が正本と一致し、例外時の応答が TS-5 を満たすか。受け入れ条件に、ゼロ埋めが効く値（1 桁の月・日・時・分・秒）と日付境界（日・月・年をまたぐ UTC→JST 換算）が含まれるか |
| 設計（software-designer） | 時刻の取得・整形・応答を分け、どこで例外が起きても時刻の形式で返す経路がない設計になっているか |
| 実装（ts-developer） | 設計どおりに取得・整形・応答が分かれ、どこで例外が起きても時刻の形式で返さないか |
| テスト（test-engineer） | 固定時刻の完全一致、取得失敗（例外）の応答、キャッシュ抑止ヘッダーを検証しているか。実時間を待っていないか |
| レビュー（code-reviewer） | 上の原則 TS-1〜TS-6 に反する経路がないか |
