# 文書の共通ルール

要求書、要件定義書、設計書、レビュー結果に共通して適用する。対象のエージェント: request-analyst、requirements-engineer、requirements-reviewer、software-designer（設計書）、code-reviewer（レビュー結果）。

## 1. フォーマット例（テンプレート）

| 文書 | 保存先 | フォーマット例 | 作成者 |
|---|---|---|---|
| 要求書 | `docs/001_requests/<NNN>_<機能名>/` | [docs/900_templates/001_request/](../../docs/900_templates/001_request/) | request-analyst |
| 要件定義書 | `docs/002_requirements/<NNN>_<機能名>/` | [docs/900_templates/002_requirements/](../../docs/900_templates/002_requirements/) | requirements-engineer |
| 設計書 | `docs/003_designs/<NNN>_<機能名>/` | [docs/900_templates/003_design/](../../docs/900_templates/003_design/) | software-designer |
| レビュー結果 | `docs/004_reviews/<NNN>_<機能名>/` | [docs/900_templates/004_review/](../../docs/900_templates/004_review/)（code-reviewer の返却を見出しごとに分ける） | メインのセッション（code-reviewer の返却を保存） |

- 文書を作る前に、必ずフォーマット例のフォルダ（`README.md` と全章）を読む。章の順番と見出し名はフォーマット例に合わせる
- フォーマット例の `<...>` は置き換える。該当がない章は削除せず「なし」と書く
- フォーマット例の「記入例」の行と、`README.md` 冒頭の HTML コメントは、そのまま残さない

### 1.1 文書の分割と名前

名前の決まりの詳細は [docs/README.md](../../docs/README.md)。ハーネスが書き込み時と `advance` 時に検査する。

| 対象 | 決まり | 例 |
|---|---|---|
| 文書 | 1 つの文書を 1 つのフォルダ `<種類のフォルダ>/<NNN>_<機能名>/` に置く。`<NNN>` は要求書のフォルダで決めた番号で、ほかの文書も同じ番号を使う | `docs/001_requests/001_time-server/` |
| 目次 | フォルダに `README.md` を置き、表題（`# <機能名> 要求書`）と章の一覧を書く | - |
| 章ファイル | 1 章（`## ` 見出し）1 ファイル。名前は `NNN_<章の見出し>.md`。番号は 001 から欠番なしで、章の順番どおり | `001_背景・目的.md` |
| 章ファイルの中身 | 1 行目を `## <章の見出し>` にする。節は `### ` で同じファイルに書く | - |

- 文書の本文は、章ファイルを番号順に連結したものとして扱う。ID の検査も連結した本文で行う
- 承認は文書のフォルダ単位で記録される。承認後にフォルダ内のファイルを変更・追加・削除・改名すると、承認を取り直す必要がある

## 2. 表形式にするもの

一覧として並ぶもの（ID を振るもの、比較するもの、対応を示すもの）は、箇条書きではなく表にする。

| 表にするもの | 例 |
|---|---|
| ID を振る項目 | 要求、決定事項、確認事項、制約、機能要件、非機能要件、受け入れ条件、未決事項、設計の構成要素 |
| 対応関係 | 要求と要件の対応、要件と設計の対応、受け入れ条件とテストの対応 |
| 仕様の一覧 | 応答の一覧（条件 × ステータス × 本文）、ヘッダー、環境変数、エラー、ログの項目 |
| 選択肢の比較 | 確認事項の選択肢、設計の代替案 |

表にしないもの:

- 背景・目的、概要など、文章で読むもの
- コードブロック（返却例、型定義、コマンド）
- 表のセルに収まらない詳細（条件の列挙、形式の細かい定義）。表には要点だけを書き、表の直後に「<ID> の補足」として箇条書きで書く

表の書き方:

- 1 行目の列は ID にする（ID がある表の場合）。ID の昇順に並べる
- セル内で改行しない。`<br>` も使わない。長くなるなら「補足」に分ける
- セルの中の `|` は `\|` と書く
- 空のセルを作らない。該当がなければ「-」と書く

## 3. ID の書式

ID の書式はハーネス（`.claude/harness/pipeline.mjs`）が検査するので変えない。番号は 1 から振り、欠番を詰めない（削除した ID は再利用しない）。

| ID | 意味 | 使う文書 | ハーネスの検査 |
|---|---|---|---|
| `REQ-n` | 要求 | 要求書 | 要求書に 1 件以上。すべて要件定義書に出てくること |
| `D-n` | 人が明示的に決めた事項（確定・合意した仮定・AI への委任範囲） | 要求書 | - |
| `Q-n` | 確認事項（ユーザーへの質問） | 要求書 | - |
| `C-n` | 制約 | 要求書 | - |
| `FR-n` | 機能要件 | 要件定義書 | 1 件以上。それぞれに受け入れ条件があること |
| `FR-n-AC-m` | 機能要件の受け入れ条件 | 要件定義書、テスト名 | すべてテスト名に出てくること |
| `NFR-n` | 非機能要件 | 要件定義書 | - |
| `U-n` | 未決事項 | 要件定義書、設計書 | - |
| `M-n` | 設計のモジュール | 設計書 | - |

注意:

- 検査は正規表現で行うため、`NFR-1` の中の `FR-1` も機能要件として数えられる。非機能要件に受け入れ条件の ID（`NFR-n-AC-m`）は振らず、非機能要件の表の「検証方法」列に書く
- 本文で ID に触れるときは、ID をそのまま書く（「上の要件」のような指し方をしない）

## 4. 書き方

- 要求・制約・要件は「4.1 根拠と決定主体」に従って出典と決定の状態を示す。要件は `REQ-n` / `D-n` / `C-n` / `Q-n` または一次資料へひも付け、設計は `FR-n` / `NFR-n` を参照する
- 根拠のない数値・機能を書かない。必要なら未決事項に「提案」として書く
- 曖昧な言葉を使わない: 「適切に」「高速に」「など」「必要に応じて」「できるだけ」「十分な」「一般的な」
- 推測で埋めない。決められないことは確認事項（要求書）か未決事項（要件定義書・設計書）に書く
- 文字列の形式は文字単位で書く（文字コード、桁数、ゼロ埋め、区切り文字、末尾改行の有無）
- 承認済みの文書を書き換えない。変更が必要なら、パイプラインで戻して承認を取り直す（[agents.md](agents.md) の「ハーネス」）

### 4.1 根拠と決定主体

「根拠区分・参照先」には、何を根拠にしたかと読み返せる箇所を書く。「決定主体・状態」には、誰がどの範囲を決め、現在どの扱いかを書く。複数の根拠が一つの項目に関わる場合は、その根拠が支える範囲を示す。資料の出典が分かっても決定者が特定できなければ、決定主体は不明と記す。

| 根拠区分 | 記録する根拠 | 決定主体・状態の書き方 |
|---|---|---|
| 人の発言 | 依頼、回答、選択結果の原文と参照先（メッセージ、Q-n、指摘 ID など） | 発言・選択で採用が明示された範囲を「人が明示決定」とし、決定者、確定または合意した仮定を記す。意向の表明や質問への未回答は未決として扱う |
| 既存仕様 | プロジェクトの仕様書、既存実装、設定の該当箇所 | 「既存仕様を適用」など適用の状態を記し、元の決定者が分かる場合は併記する |
| 他システム制約 | システム名、API 仕様・利用側の設定・確認結果の該当箇所 | 「他システム制約を適用」または「適用条件を確認中」とし、影響する接続先や環境を記す |
| AI 作成ルール | AI が設定・変更したファイルと該当箇所、変更の根拠 | AI が内容を選んだ範囲は「AI が決定」とし、適用中か暫定かを記す。委任を受けた場合はその根拠と範囲を添える |
| AI の解釈・提案 | 解釈に使った原文、提案の理由と該当する Q-n / U-n | 「未決（AI の解釈・提案）」とし、確認先を示す |
| 出典未確認 | 調べた箇所と確認できていない内容 | 決定者が不明なら「決定主体不明」と記す。判断に必要な確認は Q-n / U-n で追う |

- 決定事項（D-n）には、原文から読み取れる人の明示決定の範囲を記す。AI が文章化した場合も、原文で指定された内容と AI が補った内容を分ける。人の委任は D-n、委任の中で AI が選んだ内容は該当する要求・制約・要件に「AI が決定」と記す。AI が今回選べる範囲は依頼・委任の原文に従う。人が後から個別に採用した場合は、AI が作った案やルールの出典と人が採用した範囲をともに残す
- `CLAUDE.md` やルールファイルの記載は、既存仕様や AI 作成ルールの参照先として使う。「ユーザーの言葉（原文）」には、人が実際に述べた文または選んだ内容を出典とともに記す。選択肢を使った場合は、実際に選ばれた項目とその範囲を回答ログや会話から確認する
- AI がプロジェクトのルールを更新するときは、変更箇所、人が明示した範囲との対応、AI が選んだ内容、適用状態を、更新した文書かその変更記録に残す。要求書の制約からその箇所を参照できるようにする
- 文書全体への「承認」は文書の承認として扱う。個々の未回答事項、仮定、AI の判断は、各項目について明示された状態を引き継ぐ
- 「OS の時計のずれは許容する」という人の回答は、その範囲を D-n に記す。キャッシュ抑止に関する AI の加筆は、適用するルールとして C-n に出典とともに記す。加筆の範囲に人の判断が必要なら Q-n で確認する
- 要件定義では、根拠の ID または資料の箇所を参照し、決定主体・状態を維持する。仮定や未回答事項を使う場合は U-n を示し、参照先の本文でもその扱いが分かるようにする。旧形式の文書から引き継ぐ場合も、出典で確認できた範囲を記す

この節の変更記録（2026-11-24）。人が明示した範囲は、依頼「AIが決定したか、既存仕様か、他システム制約かどうか、人が明示的に決定したかなどは重要な違いである。これらを明示するように修正せよ」による。記録欄の構成、D-n の使い方、レビューでの照合方法は AI が決定し、文書ルール・テンプレート・担当の手順に反映した。
